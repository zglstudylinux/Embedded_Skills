# 串口监视与 AI 排错

## 核心规则

- 只基于实际抓到的日志排错。每条结论都要引用原始日志行作为证据，不要编造日志里不存在的内容。
- 乱码内容不要猜。可打印占比低时先判为"波特率不匹配或二进制协议"，用 `--baud-scan` 或 `--hex` 取证，而不是硬解码。
- **端口号与波特率是使用本 skill 的前置条件，必须由用户提供**。不同开发板的串口波特率各不相同（115200、921600、1500000 都常见），猜错会浪费联调时间甚至得出错误结论。用户没给端口时，先 `--list` 列出候选让用户选；没给波特率时直接询问，不要默认 `115200` 就开抓。
- `--auto`（自动选端口）与 `--baud-scan`（波特率扫描）只在用户明确要求"帮我找串口/猜波特率"时使用，扫描结果需用户确认后再继续。
- 抓取动作本身不改变目标板状态：不主动复位、不主动改配置。需要启动日志时用 `--wait-reset`，由用户复位或明确授权的调试器复位触发。
- 日志显示崩溃、反复重启、HardFault/断言时，如实报告并给出下一步定位建议，不要替用户"修复"。
- 复位原因标记（如 `LVD_RST`）或疑似"反复重启"只是证据，不是结论。先向用户确认刚才是否手动复位、重新上电或烧录，再判断是否真有低压/看门狗/崩溃问题。

## 工作流程

1. **向用户确认端口与波特率（前置条件，缺一不抓）**。用户给了就直接用（如 `--port COM6 --baud 1500000`）；缺端口先 `python scripts/serial_capture.py --list` 列出候选让用户选，缺波特率直接问用户。两者都明确后才进入下一步。
2. **选择抓取模式**：
   - 板子正在运行、看当前输出：`--port X --duration N`
   - 抓启动/复位日志（最常用）：`--port X --wait-reset --duration 8 --save logs/boot.log`，脚本会提示用户复位开发板
   - 验证某个标志是否出现：`--port X --wait "System Start"`
   - 乱码/二进制排查：先 `--baud-scan`，仍异常再 `--hex`
3. **运行脚本**（见 [references/usage.md](references/usage.md) 的完整参数表与示例）。
4. **AI 分析日志**，按固定四段输出：
   - `现象`：一句话概括日志表现（正常心跳/报错/循环重启/无输出/乱码）。
   - `证据`：引用关键原始日志行（错误行、启动标记、重复段落），标注时间戳。
   - `分析`：错误含义、可能原因排序；若当前工作区有源码，用错误文本反查打印位置并给出文件与行号。
   - `下一步`：按可能性排序的可执行验证动作（如"复位抓完整启动日志"、"检查 I2C 上拉"）。
5. **失败分流**（脚本失败或日志异常时）：
   - 串口打不开/拒绝访问 → `connection-failure`：端口被串口助手、IDE 占用，或端口号不对，请用户关闭占用程序。
   - 打开但 0 字节 → `no-data`：查 TX/RX 是否接反、供电、是否需要复位才有输出；用 `--wait-reset` 重试；确认波特率与开发板实际配置一致。
   - 可打印占比 < 90% → `garbled`：波特率不匹配（经用户同意后 `--baud-scan`）或二进制/加密协议（用 `--hex`）。
   - 抓到日志且有 ERROR/Fault/断言 → `target-response-abnormal`：进入第 4 步的排错输出。
6. 把确认过的端口、波特率写进后续对话上下文（`serial_port`、`baud_rate`），同会话内不要重复询问或扫描。

## 输出要求

- 汇报时给出：使用的串口、波特率、实际执行的命令、日志结论摘要；长日志给关键行，不要整段粘贴。
- 排错结论用上面第 4 步的四段格式，引用原始行做证据。
- 依赖缺失时提示 `pip install -r scripts/requirements.txt`，不要静默失败。
